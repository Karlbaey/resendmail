### 2. 交互式模式

#### 2.1 触发条件

当执行 `resendmail send` 时缺少任何必填参数（`--from`、`--to`、`--subject` 或正文来源）时，自动进入交互式模式。

#### 2.2 交互行为

**基本原则：**
- 只询问缺失的参数
- 已通过命令行参数提供的值不再询问
- 按顺序询问：from → to → cc → subject → 正文格式 → 正文输入

**询问流程：**

1. **发件人邮箱** (如果未提供 `--from`)
   - 提示："请输入发件人邮箱："
   - 实时验证邮箱格式，错误时提示并重新输入

2. **收件人邮箱** (如果未提供 `--to`)
   - 提示："请输入收件人邮箱（多个地址用逗号分隔）："
   - 实时验证所有邮箱格式，错误时提示并重新输入

3. **抄送邮箱** (总是询问，除非已通过 `--cc` 提供)
   - 提示："请输入抄送邮箱（多个地址用逗号分隔，直接回车跳过）："
   - 允许按回车跳过
   - 如果输入非空，实时验证邮箱格式

4. **邮件主题** (如果未提供 `--subject`)
   - 提示："请输入邮件主题："

5. **正文格式选择** (如果未提供任何正文来源)
   - 提示："请选择正文格式：\n  1) 纯文本\n  2) HTML\n请输入选项 (1 或 2)："
   - 验证输入必须为 1 或 2

6. **正文输入方式** (如果未提供任何正文来源)
   - 提示："请选择输入方式：\n  1) 使用编辑器输入\n  2) 从文件读取\n请输入选项 (1 或 2)："
   - 验证输入必须为 1 或 2

7. **正文内容输入**
   - **如果选择"使用编辑器输入"：**
     - 创建临时文件（使用系统临时目录）
     - 调用系统编辑器（Windows 上为 
otepad.exe`）
     - 等待编辑器关闭
     - 读取临时文件内容
     - 删除临时文件
     - 如果编辑器调用失败或文件为空，提示错误并询问："是否改为从文件读取？(y/n)"
   
   - **如果选择"从文件读取"：**
     - 提示："请输入文件路径："
     - 读取文件内容
     - 如果文件不存在或读取失败，提示错误并重新输入路径

#### 2.3 发送确认

收集完所有信息后，显示邮件汇总并要求确认：

```
=== 邮件信息确认 ===
发件人: sender@example.com
收件人: alice@example.com, bob@example.com
抄送: cc@example.com
主题: Hello World
正文格式: 纯文本
正文预览: This is the email body content... (共 500 字符)

确认发送？(y/n):
```

**汇总规则：**
- 正文预览显示前 100 字符，超出部分用 `...` 表示，并显示总字符数
- 如果用户输入 `y` 或 `Y`，执行发送
- 如果用户输入 
` 或 
`，退出程序（退出码 0）
- 其他输入提示重新输入

#### 2.4 退出机制

- 用户可以在任何时候按 Ctrl+C 中断程序
- 不显示退出提示信息
- 中断退出时使用退出码 130（标准信号退出码）

#### 2.5 timeout 处理

交互模式下始终使用默认的 10 秒超时，不询问用户。用户如需自定义可通过命令行参数 `--timeout` 提供。

#### 2.6 混合模式

交互模式与命令行参数可以混用。例如：

```bash
resendmail send --from sender@example.com --timeout 30s
```

此时只会询问缺失的 `--to`、`--subject` 和正文相关参数，已提供的 `--from` 和 `--timeout` 会被保留。

### 3. 错误处理

#### 3.1 退出码

- `0`：成功
- `1`：运行时错误（API 调用失败、缺少 API key 等）
- `2`：参数错误
- `130`：用户中断（Ctrl+C）

#### 3.2 错误输出

所有错误信息输出到 stderr，格式为 `error: <message>`。

### 4. 非功能需求

#### 4.1 可测试性

- 核心逻辑通过依赖注入（`runtimeDeps`）支持单元测试
- stdin/stdout/stderr 可注入
- 环境变量读取可注入
- 文件读取可注入
- HTTP 客户端可注入

#### 4.2 代码质量

- 通过 `gofmt` 格式化
- 通过 `go test ./...` 测试覆盖核心逻辑
- 遵循 Go 标准库风格
